# Build a project

Open the local dashboard at **http://127.0.0.1:8765/** and choose **New project** on the Projects page. The project page adds idea planning, a saved parts checklist, assembly references and progress-photo questions to the existing firmware bench.

1. Describe the idea, experience level, budget/constraints and parts already available. **Ask Meta to plan it** saves the project and makes one explicit Contributor request. Meta returns a supported draft, clarification questions or an unsupported decision.
2. Review the intended behavior, goals and suggested parts. This release uses the known classic ESP32, two separate LEDs and OLED catalog. Specifications come from local kit records. There are no live prices or verified substitute recommendations. Servo actuation, new sensors/boards, arbitrary source code and custom timing are outside the executable contract.
3. In **Parts and wiring**, tick each part you have; a tick records the required quantity as owned. Tick each assembly step as you finish it; only the next step shows its instructions. Ticks save immediately and are your own report, not a hardware check. The wiring diagram shows logical connections, not the physical carrier layout.
4. Accepting the brief, which happens automatically when you approve a plan, freezes that version's intended behavior and hash, then sends the brief's firmware intent to the planner in the same click (one explicit Meta request) and opens the plan page. If Muse Spark asked a question instead, answer it in the reply box under the question; the brief updates and the button appears. Later advice leaves it fixed. A revised brief is shown for explicit review/acceptance; earlier accepted versions remain in history.
5. Ask a question or add up to three JPEG/PNG progress photos. The browser resizes them to at most 1600 pixels on the long edge. Export HEIC as JPEG first. Select **Ask Meta** to send the question, selected photos and project context. Images are saved locally; previous photo descriptions remain historical and previous image bytes are not silently resent.
6. **Use iPhone camera** enumerates devices and requires explicit Continuity Camera selection. Capture uses the existing native helper for ten seconds, opens no serial connection and makes no model request. The preview is attached locally; **Ask Meta** is the separate transmission action. Camera acquisition shares the single bench owner with build/install/test jobs.
7. Optionally select recorded test evidence for an explanation. Its frozen expected steps, geometry rejections and findings are supplied as historical evidence. It is explicitly unlinked to the current project; the guide must not substitute the current project's goals. The conversation links back to the actual test. Explanations and photo observations are advisory, not automatic measurements or physical pass verdicts.
8. Coming back later, the brief card shows one next step and one button, **Open plan & bench →**. **Prepare a new plan** sends the accepted behavior to the planner again as a separate explicit API request. Inspect/review the proposal, then use the existing Compile, Install and Camera test actions. No hardware operation is hidden in planning or guidance.

After a reviewed proposal compiles, expand **Firmware source & downloads** to inspect the actual PlatformIO sources, rendered behavior table, build log and binary hash. Download the source ZIP or firmware binary. Meta proposes behavior data; trusted local code renders the C++ table and supplies the runtime. This feature does not claim unrestricted Meta-written C++.

The **Details and recent jobs** line under the brief tracks the accepted brief, linked proposal, compiled version, recorded installed application and its ID-only runtime check. It shows camera behavior separately. Open a recent job for logs and recovery guidance, including failed builds. **Open plan & bench →** continues the linked proposal without another planning request. Installation includes a post-flash idle identity check; the explicit recheck sends only ID and does not reflash or execute the sequence.

Project state and conversations survive restart under `runs/projects/{id}/`. Accepted briefs and firmware-proposal links retain their hashes. Turn requests/responses, image hashes, actual latency and returned token usage are retained. Project/turn/image integrity is checked when read. Browsing saved work makes no model calls. Requests are serialized within the guide; duplicate IDs reuse the request, failures have no automatic retry or provider fallback, and interrupted requests never resume automatically. The existing Contributor key remains server-side.

The guide is separate from the frozen OLED measurement reader. Guidance can receive expected behavior to explain a failure; the measurement reader continues to receive only its image crops and unchanged transcription prompt. Physical camera-reference refresh and full servo calibration remain separate pending stages. A photo cannot establish electrical continuity, voltage or calibrated angles.
